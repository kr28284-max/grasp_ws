현재 데이터로는 “카메라 좌표계 기준의 근사 6D pose”를 계산할 수 있습니다. 특히 박스·벽돌처럼 방향성이 뚜렷한 물체라면 PCA 방식이 적합합니다.

처리 흐름은 다음과 같습니다.

```text
YOLO segmentation mask
        ↓
마스크 내부 Depth 추출
        ↓
3D point cloud 생성
        ↓
노이즈 및 바닥면 제거
        ↓
중심 위치 XYZ 계산
        ↓
PCA로 물체 방향축 계산
        ↓
회전행렬 → Quaternion
        ↓
PoseStamped 발행
        ↓
camera frame → robot base frame TF 변환
```

### 1. 위치 XYZ

현재 생성한 포인트 클라우드의 평균보다 중앙값이 노이즈에 강합니다.

```python
position = np.median(points, axis=0)
```

결과는 카메라 좌표계 기준 미터 단위입니다.

```text
x: 카메라 오른쪽
y: 카메라 아래쪽
z: 카메라 전방
```

### 2. 자세 Roll, Pitch, Yaw

포인트 클라우드에 PCA를 적용합니다.

```python
centered = points - position
covariance = np.cov(centered, rowvar=False)

eigenvalues, eigenvectors = np.linalg.eigh(covariance)
order = np.argsort(eigenvalues)[::-1]
axes = eigenvectors[:, order]

x_axis = axes[:, 0]  # 물체의 가장 긴 방향
z_axis = axes[:, 2]  # 표면 법선 방향
y_axis = np.cross(z_axis, x_axis)

x_axis /= np.linalg.norm(x_axis)
y_axis /= np.linalg.norm(y_axis)
z_axis = np.cross(x_axis, y_axis)

rotation_matrix = np.column_stack((x_axis, y_axis, z_axis))
```

이 회전행렬을 Quaternion으로 변환해 `geometry_msgs/PoseStamped`로 발행하면 됩니다.

```python
from geometry_msgs.msg import PoseStamped
from scipy.spatial.transform import Rotation

quaternion = Rotation.from_matrix(rotation_matrix).as_quat()

pose = PoseStamped()
pose.header = rgb_msg.header

pose.pose.position.x = float(position[0])
pose.pose.position.y = float(position[1])
pose.pose.position.z = float(position[2])

pose.pose.orientation.x = float(quaternion[0])
pose.pose.orientation.y = float(quaternion[1])
pose.pose.orientation.z = float(quaternion[2])
pose.pose.orientation.w = float(quaternion[3])
```

추천 출력 토픽은 다음과 같습니다.

```text
/grasp/target_pose
```

### 3. 로봇 좌표계로 변환

지금 계산되는 pose는 `camera_color_optical_frame` 기준입니다. 로봇이 사용하려면 카메라와 로봇 사이의 외부 캘리브레이션이 필요합니다.

```text
camera_color_optical_frame → base_link
```

`tf2_ros`로 변환하면 최종적으로 `base_link` 기준 pose를 얻을 수 있습니다.

### 중요한 제한

단일 카메라에서 보이는 표면만 이용하므로 완전한 물체 자세와는 차이가 생길 수 있습니다.

- 박스, 벽돌: PCA로 비교적 안정적
- 원통, 구: 회전 방향 자체가 모호함
- 물체 일부가 가려짐: 중심과 방향이 편향됨
- PCA 축은 순간적으로 180° 뒤집힐 수 있음
- 물체의 pose와 실제 로봇 grasp pose는 서로 다를 수 있음

따라서 벽돌처럼 테이블 위에 놓인 물체라면 보통 다음처럼 제한하는 것이 더 안정적입니다.

- Roll/Pitch는 테이블 법선에 맞춤
- Yaw만 PCA의 가장 긴 축으로 계산
- Z는 포인트 중앙값 또는 물체 상단 높이로 계산
- 그리퍼 접근 방향은 테이블 위에서 아래 방향으로 고정

CAD 모델 기준의 정확한 6D object pose가 필요하다면 PCA가 아니라 모델 정합, 특징점 기반 pose estimation 또는 FoundationPose 같은 별도 6D pose 추정기가 필요합니다. 현재 구조에는 우선 `PCA 기반 /grasp/target_pose` 발행을 붙이는 것이 가장 현실적인 다음 단계입니다.



근데 내가 하고싶은건 물체의 완전한 6dpose를 잡고싶은건데 지금 듀플로블럭같은경우는 세그멘테이션도 잘되고 포인트 클라우드도 어느정도 찍히는거같은데 그럼 물체를 사선에서 보면 더 잘잡을수 있을까? 그리고 물체의 좌표계같은것도 따로 지정을 해줘야해?


사선에서 촬영하면 Duplo 블록의 6D pose 추정에 유리합니다. 다만 세그멘테이션과 부분 포인트 클라우드만으로는 가려진 면까지 포함한 “완전한 6D pose”를 유일하게 결정할 수 없습니다. 블록의 크기나 CAD 모델 같은 사전 정보가 필요합니다.

### 카메라 각도

정면 또는 수직 위에서만 보면:

- 윗면만 보여 Roll/Pitch 판단이 어려움
- 직사각형 블록의 앞뒤 방향이 모호함
- 높이와 측면 형상 정보가 부족함

카메라를 기울여 윗면과 두 측면이 같이 보이게 하면:

- 세 축 방향을 더 안정적으로 추정
- 블록 높이와 옆면 형상 확인 가능
- 모델 정합 시 대응점 증가

추천 구도는 테이블 수직 방향에서 약 30~45° 기울여 블록의 윗면과 인접한 측면 두 개가 보이도록 하는 것입니다. 너무 낮은 각도에서는 윗면이 가려지고 Depth 노이즈가 증가할 수 있습니다.

### 물체 좌표계는 반드시 정의해야 합니다

6D pose는 결국 다음 변환을 구하는 것입니다.

```text
camera_color_optical_frame → duplo_object_frame
```

Duplo 좌표계는 예를 들어 이렇게 고정할 수 있습니다.

```text
원점: 블록 바닥면의 기하학적 중심
X축: 블록의 긴 방향
Y축: 블록의 짧은 방향
Z축: 스터드가 향하는 위쪽 방향
```

그러면 출력 pose의 의미가 명확해집니다.

```text
position = 카메라에서 블록 원점까지의 XYZ
orientation = 카메라 좌표계에 대한 블록 XYZ축의 회전
```

로봇이 사용하려면 최종적으로 다음 변환이 필요합니다.

```text
T_base_object = T_base_camera × T_camera_object
```

여기서 `T_base_camera`는 카메라-로봇 외부 캘리브레이션으로 구해야 합니다.

### Duplo에 추천하는 추정 방식

현재 시스템에는 다음 방식이 가장 현실적입니다.

1. YOLO로 Duplo 마스크 추출
2. 마스크 내부 RGB-D 포인트 클라우드 생성
3. 테이블 평면과 노이즈 제거
4. PCA/OBB로 대략적인 초기 자세 계산
5. 실제 Duplo CAD 또는 치수 기반 3D 모델과 정합
6. ICP로 위치와 회전 정밀 보정
7. `/grasp/target_pose`로 `PoseStamped` 발행
8. TF로 `base_link` 좌표계로 변환

PCA만 사용하면 “대략적인 방향”이고, 모델 정합까지 해야 물체 좌표계 기준의 6D pose가 됩니다. Duplo처럼 규격화된 물체는 CAD가 없어도 정확한 가로·세로·높이 치수로 직육면체 모델을 만들 수 있습니다. 스터드 형상까지 모델에 포함하면 윗면 방향 판별이 더 안정적입니다.

### 대칭성 문제

예를 들어 단색 2×4 Duplo는 180° 돌려도 형상이 같습니다. 이런 경우 영상과 Depth만으로는 다음 두 자세를 구분할 수 없습니다.

```text
Yaw = 0°
Yaw = 180°
```

이는 알고리즘 오류가 아니라 물체 자체의 대칭성 때문입니다. 따라서 다음 중 하나로 처리해야 합니다.

- 두 자세를 동일한 유효 pose로 취급
- 스터드, 로고, 색 패턴 등 비대칭 특징 사용
- 시간에 따른 이전 pose와 비교해 방향 유지
- 로봇 grasp에 유리한 대칭 자세를 선택

결론적으로, 사선 촬영은 도움이 되지만 핵심은 `Duplo 물체 좌표계 정의 + 실제 치수/CAD 모델 + 부분 포인트 클라우드 모델 정합 + 카메라-로봇 캘리브레이션`입니다. 현재 CPU 기반 구성에는 Open3D의 초기 정합 및 ICP를 붙이는 방식이 가장 구현하기 좋습니다.


지금 어떤 상황이냐면 망치랑 듀플로 블루 4x2블럭의  세그멘테이션은 완벽하게 찍히는데 포인트 클라우드도 나오는데 일단 포인트 클라우드가 정확하기 찍히는거같진않고 잘 모르겠어 그리고 이제 해야할거는 포인트 클라우드가 찍히긴 하는데 모양이 카메라 컬러화면이랑 동일하게 나오진 않아 뒤집어져 있는 느낌? (이부분은 카메라 좌표계가 현실 좌표계랑 달라서 그런건가? ) 그리고 6Dpose를 뽑으려면 1. 물체 좌표계 설정(이건 물체의 치수재서 미리 코드에 대입해줘야 하나? 그리고 계산해서 물체의 pose맞는지 확인? ) 2. 테이블 평면이랑 노이즈 제거 3. 초기자세 계산 4. \~\~\~ 4번 이후로는 잘모르겠는데 일단 내가 이해한게 맞나?


이해한 방향은 거의 맞습니다. 다만 6D pose 계산 전에 “현재 포인트 클라우드가 올바른지 검증하는 단계”가 반드시 먼저 들어가야 합니다.

### 포인트 클라우드가 뒤집혀 보이는 이유

현재 포인트 계산식은 ROS 카메라 optical frame 기준입니다.

```text
X: 영상 오른쪽
Y: 영상 아래쪽
Z: 카메라 전방
```

일반적인 로봇 좌표계는 보통 다음과 같습니다.

```text
X: 전방
Y: 왼쪽
Z: 위쪽
```

따라서 RViz에서 외부 시점으로 보면 뒤집히거나 회전된 것처럼 느껴질 수 있습니다. 특히 포인트 클라우드의 뒤쪽에서 바라보고 있으면 좌우가 거울처럼 보입니다.

현재 코드의 다음 계산은 optical frame 기준으로 정상입니다.

```python
x = (u - cx) * z / fx
y = (v - cy) * z / fy
z = depth
```

단순히 `y = -y`처럼 바꾸면 안 됩니다. 그렇게 하면 `camera_color_optical_frame`이라는 헤더 정보와 실제 데이터 방향이 달라집니다. 로봇 좌표계 변환은 나중에 TF가 담당해야 합니다.

그리고 3D 포인트 클라우드를 사선에서 보면 2D 컬러 영상의 실루엣과 모양이 달라지는 것은 자연스럽습니다. 컬러 영상과 동일한 카메라 시점에서 투영했을 때 마스크와 일치해야 정상입니다.

### 가장 먼저 해야 하는 검증

현재 3D 포인트를 다시 2D 영상으로 역투영합니다.

```python
u_check = fx * x / z + cx
v_check = fy * y / z + cy
```

이 좌표들이 원래 세그멘테이션 마스크 픽셀에 정확히 들어가야 합니다.

```text
3D point 생성
    ↓
다시 RGB 영상으로 투영
    ↓
원래 segmentation mask와 비교
```

일치하지 않으면 다음 중 하나가 문제입니다.

- RGB와 Depth 정렬 오류
- RGB와 Depth 시간 동기화 오류
- 잘못된 CameraInfo 사용
- YOLO 마스크 리사이즈 오류
- Depth 단위 변환 오류
- 잘못된 RViz frame 설정

포인트에 원래 RGB 픽셀 색상을 넣어 colored point cloud로 표시하면 정렬 상태를 훨씬 쉽게 확인할 수 있습니다.

### 물체 좌표계와 치수는 별개입니다

물체 좌표계를 정의하는 것 자체에는 치수가 필요하지 않습니다. 원점과 축의 의미만 정하면 됩니다.

Duplo 4×2 블록은 다음처럼 정의할 수 있습니다.

```text
원점: 블록 바닥면의 기하학적 중심
X축: 블록의 긴 방향
Y축: 블록의 짧은 방향
Z축: 스터드가 향하는 방향
```

망치는 예를 들면:

```text
원점: 망치 머리와 손잡이가 연결되는 중심
X축: 손잡이 끝 방향
Y축: 망치 머리의 좌우 방향
Z축: X와 Y로 결정되는 위쪽 방향
```

치수나 CAD 모델은 그다음 모델 정합 단계에서 필요합니다. 즉:

- 좌표계 정의: pose의 기준을 결정
- 치수/CAD 모델: 관측된 포인트와 물체 모델을 맞추는 데 사용

### 권장 전체 순서

#### 0. 포인트 클라우드 정확도 검증

- 3D → 2D 재투영
- RGB 색상이 포함된 포인트 클라우드 표시
- Depth 최솟값, 중앙값, 최댓값 확인
- RViz Fixed Frame을 `camera_color_optical_frame`으로 설정
- 세그멘테이션 경계와 Depth 경계 비교

#### 1. 물체별 좌표계와 3D 모델 정의

Duplo와 망치 각각 별도로 정의해야 합니다.

- 원점
- X/Y/Z축
- 실제 치수
- CAD 또는 단순화된 형상 모델
- 대칭 가능한 회전

#### 2. 테이블과 노이즈 제거

일반적인 처리 순서는 다음과 같습니다.

```text
Voxel downsampling
→ RANSAC 테이블 평면 검출
→ 테이블 포인트 제거
→ Statistical outlier 제거
→ 가장 큰 object cluster 선택
```

단, YOLO 마스크 안에 물체만 정확히 들어온다면 테이블 제거는 보조적인 역할입니다.

#### 3. 초기 자세 계산

Duplo가 테이블에 정상적으로 놓여 있다면:

- 위치: 포인트 중앙값 또는 모델 중심
- Z축: 테이블 평면 법선
- X축: OBB/PCA의 긴 방향
- Y축: `Z × X`

이 경우 실제로는 Roll/Pitch가 테이블에 의해 거의 결정되므로 `X, Y, Z, Yaw` 중심으로 먼저 추정할 수 있습니다.

망치는:

- PCA의 가장 긴 축으로 손잡이 방향 추정
- 망치 머리 포인트로 앞뒤 방향 판별
- 테이블 법선으로 위쪽 축 결정

다만 PCA 결과는 어디까지나 모델 정합을 시작하기 위한 초기값입니다.

#### 4. 물체 모델 정합

초기 pose로 CAD 포인트 클라우드를 이동시킨 다음 관측 포인트에 맞춥니다.

```text
초기 pose
→ 여러 대칭 pose 후보 생성
→ ICP 정합
→ fitness와 RMSE 비교
→ 가장 잘 맞는 pose 선택
```

부분 포인트 클라우드이므로 일반 ICP보다 point-to-plane ICP와 robust loss가 유리합니다.

#### 5. pose 신뢰도 검사

다음 조건을 통과한 경우에만 pose를 발행해야 합니다.

- ICP fitness가 기준 이상
- RMSE가 기준 이하
- 유효 포인트 수 충분
- 물체 치수와 관측 크기가 유사
- 위치가 작업 공간 내부
- pose가 이전 프레임에서 갑자기 뒤집히지 않음

#### 6. 결과 시각화

숫자만 확인하면 pose가 맞는지 판단하기 어렵습니다. RViz에 다음을 표시해야 합니다.

- 관측된 물체 포인트 클라우드
- 추정 pose의 XYZ 좌표축
- 추정 pose로 변환한 CAD 모델
- 물체 중심점
- 최종 grasp pose

CAD 모델이 실제 포인트 클라우드와 겹치면 pose가 맞는 것입니다.

#### 7. 로봇 좌표계로 변환

마지막으로:

```text
T_base_object = T_base_camera × T_camera_object
```

카메라가 고정되어 있다면 eye-to-hand 캘리브레이션, 로봇 손목에 있다면 hand-eye 캘리브레이션이 필요합니다.

### Duplo와 망치에서 중요한 차이

Duplo는 치수가 명확하고 직육면체라 모델 정합이 쉽지만 180° 대칭 문제가 있습니다. 망치는 비대칭이라 방향 구분은 가능하지만 손잡이가 가늘고 가려지기 쉬워 부분 포인트 클라우드 정합이 더 어렵습니다.

따라서 지금 가장 먼저 할 일은 6D pose 계산이 아니라 다음 두 가지입니다.

1. 포인트 클라우드를 RGB 색상과 함께 표시  
2. 3D 포인트를 2D 마스크로 재투영해 정렬 정확도 검증

이 검증이 끝난 뒤 `노이즈 제거 → 초기 pose → 모델 정합 → pose 좌표축/CAD 시각화 → 로봇 좌표 변환` 순서로 가는 것이 맞습니다.
